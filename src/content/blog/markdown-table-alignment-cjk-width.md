GitHub README 里的表格，源码往往是每一列都手工对齐的：

```markdown
| 姓名   | 部门   | 工资    |
| ------ | ------ | ------- |
| Alice  | Eng    | 120000  |
| 张三   | 销售   | 98000   |
```

中文一进来，这件事立刻变得不可救药：`张三` 在源码里只占 2 个字符，在等宽字体里却渲染成 4 列宽——用字符数补空格，表格在编辑器里永远歪的；用显示宽度补，渲染结果又不受影响（Markdown 表格的竖线位置不参与渲染），纯为源码可读性服务。要补对，必须先回答"每个字符显示宽度是多少"。

## 东亚宽度：同一个 Unicode，两套标尺

Unicode 给每个码位标了一个 East Asian Width（东亚宽度）属性，关键的几类：

- **W（Wide）/ F（Fullwidth）**：显示宽度 2。汉字、全角标点（，。：；！？）、全角字母数字；
- **Na（Narrow）/ H（Halfwidth）**：显示宽度 1。ASCII、半角片假名；
- **A（Ambiguous）**：看环境。`± × ÷ ° · §` 这批字符在西方语境宽度 1，在东亚字体里宽度 2——对齐算法里最烦的一类，工具必须选边站；
- **emoji**：绝大多数显示宽度 2，但有些实现按 1 处理，跨平台差异最大。

所以"张三"显示宽度是 4，"Ａｌｉｃｅ"（全角）是 10，而 `"±1"` 在不同终端里可能是 2 也可能是 3。一个可靠的对齐工具需要逐码位查 East Asian Width 表，而不是数 `.length`。

## `.length` 数的是 UTF-16 码元，不是字，更不是宽度

JavaScript 的 `str.length` 数 UTF-16 码元：`'张'.length === 1`，但 `'𝕊'.length === 2`（代理对），`'👨‍👩‍👧'.length === 8`（三个 emoji 加两个零宽连接符）。用它做对齐，任何含 emoji 或罕见字符的表格都会歪。同理：

- `[...str]`（按码点迭代）解决了代理对，但一个码点仍不等于一个用户感知字符（组合字符序列）；
- 显示宽度还要再叠一层：零宽字符（ZWJ、U+200B）宽度是 0，组合附标不占新列；
- 现代标准是 `Intl.Segmenter` 按"字素簇"切分 + East Asian Width 查表求宽——两件事缺一不可。

这也解释了为什么多数编辑器的表格格式化在中英混排时靠不住：它们中的不少仍在按 `.length` 或码点数补空格。

## 表格美化还躲不开转义与结构规则

宽度之外还有两条容易翻车的规则：

1. **竖线必须转义**：单元格文本里的 `|` 要写成 `\|`，否则被当成列分隔符，整行列数悄悄错位；
2. **列数以分隔行为准**：`| --- | --- |` 定义两列，数据行多写一个单元格并不会多出一列，多余部分被丢弃；少写的自动补空。格式化工具应该在补空格之前先核对每行列数与分隔行一致，而不是默默修好。

对齐方向同样写在分隔行里：`| :--- |` 左对齐、`| :---: |` 居中、`| ---: |` 右对齐——格式化要保留它们，不能一刀切成左对齐。
